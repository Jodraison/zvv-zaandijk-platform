**ZVV Zaandijk VRZ1 — Football Academy**

**Status:** Definitief · Geen implementatie · Geen code

## 0. Wat dit document is

Vanaf **PB13** schrijf je **geen gewone Playbooks** meer. Je schrijft de **definitieve Academy** — jarenlang bruikbaar, elke entry **beter dan de vorige**.

**Ondergrens kwaliteit:** PB11 + PB12 (inhoudelijke diepte, kettingdenken, zaterdagtransfer).  
**Bovenliggende eisen:** taal, lengte, Praatje→Plaatje→Daadje, 4e-klas-toegankelijkheid, **teamtransfer**.

| Publiek | Realiteit |
|---------|-----------|
| Leeftijd | 16–35 (4e klas tot senioren) |
| Training | 2× per week |
| Wedstrijd | 1× per week |
| Tijd | Werken/studeren — **enkele minuten** per sessie lezen |
| Geen | UEFA-cursus · voetbaljargon · indruk maken |

**Regel:** NOOIT schrijven om indruk te maken. ALTIJD schrijven zodat **zij** zaterdag beter voetbalt — en **wij als team** zaterdag anders functioneren.

## 1. De enige succesvraag

De Academy beantwoordt uiteindelijk **één vraag**:

> **Wat doet ons complete team zaterdag anders?**

Niet alleen: *wat doet de linksback?* — maar ook: *wat doet de verdediging · het middenveld · de aanval · het complete team?*

### Drie niveaus (alle drie verplicht)

| Niveau | Vraag | Faal = |
|--------|-------|--------|
| **Individu** | Wat doet **deze** speelster zaterdag aantoonbaar beter? | Herschrijven |
| **Linie** | Wat doet **haar linie** collectief anders? | Herschrijven |
| **Team** | Wat doet **ons team** collectief anders? | Herschrijven |

Kan één niveau **niet objectief** beantwoord worden? → **Niet publiceren.**

### Formaat — individu (max. 3 per speelster)

```markdown
## Zaterdag — wat jij anders doet

• [werkwoord + context + observeerbaar]
• [max 2]
• [max 3]
```

**Maximaal drie.** Geen “zij begrijpt…”. Alleen gedrag.  
Meer dan drie per speelster = te veel — **focus snijden**.

### Formaat — team (verplicht einde Playbook)

Zie **§17 Team Performance Layer** — blokken **Linie-transfer** + **Team-transfer** + **Validaties**.

## 3. Schrijfregels — twaalf vragen (geen uitzondering)

Iedere **uitleg-eenheid** beantwoordt:

| # | Vraag |
|---|-------|
| 1 | Wat gebeurt er? |
| 2 | Waarom gebeurt dit? |
| 3 | Waaraan herken ik dit? |
| 4 | Wat wordt er van **mij** verwacht? |
| 5 | Waarom juist van **mij**? |
| 6 | Wat doet **mijn linie**? |
| 7 | Wat doet het **team**? |
| 8 | Wat doet de **tegenstander**? |
| 9 | Wat **probeert** de tegenstander? |
| 10 | Hoe **reageren wij**? |
| 11 | Wat als ik het **niet** doe? |
| 12 | Wat als ik het **wél** goed doe? |

**Niet in proza verstoppen.** Gebruik compacte blokken waar het kan — maar **alle twaalf** moeten beantwoord zijn.

## 4. Geen theorie — alleen oorzaak → gevolg

### Verboden

> “Een back moet breed blijven.”  
> “Ze begrijpen het beter.”

### Verplicht

> “Jij blijft breed omdat hun rechtsbuiten dan moet kiezen. Komt zij naar jou, dan ontstaat ruimte voor onze nummer 10. Blijft zij staan, dan kun jij de bal ontvangen. **Daarom** blijf jij breed.”

**Teamketting (elke belangrijke actie):**

```
Speler
  ↓
Linie
  ↓
Team
  ↓
Tegenstander
  ↓
Nieuwe ruimte
  ↓
Nieuwe beslissing
```

Minimaal **5 treden**. Geen losse tip.

## 7. Praatje → Plaatje → Daadje (exacte volgorde)

Iedere uitleg-eenheid:

### 1. Praatje

- Eenvoudige uitleg · alsof je naast haar staat  
- Geen jargon · korte zinnen  
- Max. **120 woorden** per eenheid (richtlijn)

### 2. Plaatje

- Minimaal **één** visual per belangrijke eenheid  
- Alleen als het **gedrag** verandert

### 3. Daadje

- Exact wat zij **zaterdag** doet — werkwoord, moment, trigger

**Geen Plaatje zonder Praatje. Geen Daadje zonder Plaatje.**

---

## 8. Visuals — alleen als gedrag verandert

Voor **elke** visual — vijf vragen:

| # | Vraag |
|---|-------|
| V1 | Waarom bestaat deze visual? |
| V2 | Welke **fout** voorkomt hij? |
| V3 | Wat **ziet** de speelster? |
| V4 | Wat doet zij **daarna anders**? |
| V5 | Verandert zaterdaggedrag **zonder** deze visual? |

**Eén zwak antwoord → visual weg.**

**Geen geïmplementeerde afbeelding = Playbook niet publiceerbaar** (alleen T##-tekst telt niet).

## 17. Team Performance Layer (TPL)

**Verplicht aan het einde van elke Playbook (PB13+).**  
Cursor controleert dit **na** het schrijven — vóór publicatie.

Geen theorie. Alleen concreet, observeerbaar gedrag.

---

### TPL-1 · Individuele transfer

**Controle:** Na deze Playbook kan **iedere** speelster maximaal **drie** concrete gedragingen uitvoeren.

| Regel | Toets |
|-------|-------|
| Max. 3 per speelster | Niet meer — anders focus snijden |
| Objectief waarneembaar | Werkwoord + moment + trigger |
| Per positie expliciet | §7 of samenvattend blok |

**Formaat:**

```markdown
### Individuele transfer

| Positie | Zaterdag max. 3 |
|---------|-----------------|
| Keeper | • … · • … · • … |
| LCV | • … |
| … (alle 11) | |
```

**Faal:** meer dan 3 · vage formulering (“beter positioneren”) · niet per positie.

---

### TPL-2 · Linie-transfer

**Controle:** Wat verandert **collectief** per linie?

**Formaat — geen proza-theorie:**

```markdown
### Linie-transfer

**Verdediging — zaterdag anders:**
• [collectief gedrag 1]
• [collectief gedrag 2]
• [max 3]

**Middenveld — zaterdag anders:**
• …

**Aanval — zaterdag anders:**
• …
```

**Voorbeelden (observeerbaar):**
- verdediging schuift **samen** eerder door na switch
- middenveld houdt **kortere** afstand tussen L6 en R6 onder druk
- aanval bindt **langer** hun centrale verdediger voordat wij switchen

**Faal:** losse individuele tips zonder collectief effect.

---

### TPL-3 · Team-transfer

**Controle:** Wat verandert voor het **complete team**?

```markdown
### Team-transfer — zaterdag anders

• [teamgedrag 1 — observeerbaar]
• [teamgedrag 2]
• …
• [max 5–7 — elk meetbaar]
```

**Voorbeelden (goed):**
- team schuift eerder door
- team herkent pressing eerder
- team houdt betere afstanden tussen linies
- team communiceert eerder (“man op”, “switch”, “rustig”)
- team creëert vaker overtal
- team houdt beter restverdediging
- team speelt rustiger onder druk

**Faal:** “wij spelen beter uit” zonder meetbaar signaal.

---

### TPL-4 · Trainer Validation

**Controle:** Kan de trainer dit **objectief zien** op zaterdag?

```markdown
### Trainer Validation — wat ik zaterdag zie

| # | Ik zie… | Ja/Nee op zaterdag |
|---|---------|---------------------|
| T1 | keeper coacht eerder | |
| T2 | backs blijven langer breed | |
| T3 | dubbele 6 draait eerder open | |
| … | min. 5 meetpunten | |
```

**Minimaal 5 meetpunten** gekoppeld aan TPL-2 en TPL-3.

**Verboden:** “Ze begrijpen het beter.” · “Het voelt rustiger.” zonder observeerbaar signaal.

**Faal:** trainer kan Playbook niet afvinken aan de lijn.

---

### TPL-5 · Captain Validation

**Controle:** Kan de **aanvoerder** deze Playbook in **minder dan één minuut** samenvatten voor het team?

```markdown
### Captain Validation — 60 seconden

**Zeg tegen je team:**
“[3–5 zinnen — wat wij zaterdag anders doen als team]”
```

**Faal:** captain heeft jargon nodig · langer dan 60 sec · kan linie-transfer niet noemen.

→ **Uitleg vereenvoudigen.**

---

### TPL-6 · Peer Validation

**Controle:** Kan een speelster na **training** deze Playbook uitleggen aan een **teamgenoot**?

```markdown
### Peer Validation — uitleg aan teamgenoot

**Zij moet kunnen zeggen:**
1. Wanneer herken ik het? (1 zin)
2. Wat doe ik? (max 3)
3. Wat doet ons team? (max 3)
```

**Faal:** teamgenoot snapt het niet · peer moet Playbook erbij pakken.

→ **Herschrijven.**

---

### TPL-7 · Simplicity Validation

**Controle expliciet:**

> Kan een gemiddelde **4e klasse-speelster** die 2× per week traint, 1 wedstrijd speelt, en daarnaast werkt/studeert — de inhoud binnen **enkele minuten** begrijpen **én** zaterdag toepassen?

| NEE → actie |
|-------------|
| Verwijder theorie |
| Eenvoudiger taal |
| Herkenbare wedstrijdsituaties toevoegen |
| Meer visuals |
| Kortere uitleg (Praatje ≤ 120 woorden) |
| Individuele transfer terug naar max 3 |

**Formaat:**

```markdown
### Simplicity Validation

| Check | Ja/Nee |
|-------|--------|
| 🟢-pad ≤ 3 min totaal | |
| Geen jargon zonder uitleg | |
| Minuut/scenario herkenbaar | |
| Max 3 gedragingen per speelster | |
| Team-samenvatting ≤ 60 sec | |
```

## 18. Publicatiegate — team (uitbreiding)

**Eén NEE = geen publicatie.**

Na **§14 (individu)** én **§17 (TPL)** moeten **alle** vakjes JA zijn:

| # | Criterium |
|---|-----------|
| P1 | Individuele speelster wordt **objectief** beter (TPL-1) |
| P2 | **Verdediging** werkt collectief beter (TPL-2) |
| P3 | **Middenveld** werkt collectief beter (TPL-2) |
| P4 | **Aanval** werkt collectief beter (TPL-2) |
| P5 | **Complete team** functioneert beter (TPL-3) |
| P6 | Trainer kan het **objectief waarnemen** (TPL-4) |
| P7 | Captain kan het in **< 60 sec** uitleggen (TPL-5) |
| P8 | Teamgenoot kan het **navertellen** na training (TPL-6) |
| P9 | Inhoud **realistisch** op 4e klasse-niveau (TPL-7) |
| P10 | Alle **§14 E1–E15** = JA |

**Publicatie = P1–P10 alle JA.**

## 19. Waarom v1.1 de Academy sterker maakt

| Probleem v1.0 | Oplossing v1.1 |
|---------------|----------------|
| Elf posities · los van elkaar | **Linie + team** maken duidelijk hoe posities **samen** werken |
| “Begrijpen” als succes | **Trainer/Captain/Peer** dwingen meetbaarheid af |
| Te veel gedragingen | **Max 3** per speelster = focus op zaterdag |
| Individu vs team | Eén ketting: speler → linie → **team** → tegenstander |
| Academy = solo lezen | **Peer Validation** = team leert team |
| Theorie sijpelt door | Simplicity Validation + captain-test filteren complexiteit |

**Resultaat:** Een speelster leest minuten · captain vat minuten samen · trainer ziet het team veranderen · zaterdag speelt **ZVV** anders — niet elf individuen.

## 20. Eindvalidatie — definitieve ontwikkelstandaard?

| Vraag | Antwoord |
|-------|----------|
| Individu + linie + team gedekt? | **Ja** — §1 · §17 · §18 |
| 4e klas realistisch? | **Ja** — §12 · TPL-7 · max 3 |
| Geen nieuwe engine? | **Ja** — alleen FDPS v1.1 |
| Meetbaar voor trainer? | **Ja** — TPL-4 |
| Team draagt kennis? | **Ja** — TPL-5 · TPL-6 |
| Publicatiegate compleet? | **Ja** — P1–P10 |
| Nog open na v1.1? | **Product** (visuals renderen · playbooks in app) — buiten FDPS |
| **Bevriezen als schrijfstandaard?** | **Ja** — FDPS v1.1 is **definitief** voor PB13–PB35. Alleen **patch** (v1.1.x) bij bewezen lacune; geen v2.0 zonder teamconsensus. |

**Conclusie:** FDPS v1.1 kan worden **bevroren** als definitieve ontwikkelstandaard voor Academy-inhoud. Volgende werk = **PB13 schrijven** onder deze standaard — niet de standaard verder uitbreiden.
